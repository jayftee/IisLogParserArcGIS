# IIS Log Parser for ArcGIS

Status: ready-for-agent

## Problem Statement

The organization runs ArcGIS Server and Portal behind IIS and needs to understand daily usage — which endpoints, ArcGIS services, referers, user agents, and client IPs are driving load, and how that ArcGIS Server traffic is performing (success/failure rates) — but today only has raw, daily-rotated IIS W3C log files to work from. Keeping raw log rows around indefinitely isn't wanted, and there's no reliable, tested pipeline that turns a day's raw log lines into small, queryable daily aggregate tables. Re-running a day's processing (e.g. after a bug fix) also risks silently duplicating or double-counting that day's totals if the pipeline isn't built to replace rather than append.

## Solution

A C# console application, invoked once per day (e.g. via Windows Task Scheduler) with the log source directory, a target local date, and an output SQLite database path. It discovers the correct log file(s) for that local day (including the adjacent UTC-dated file needed to fully cover local-day boundaries), parses and normalizes each line using that file's own declared field schema, computes seven aggregate dimensions in memory for the day, and atomically replaces that day's rows in the output database. It fails loudly (non-zero exit, clear message) when no input is found, and reports a run summary (lines parsed/valid/invalid, elapsed time) so operational problems are visible immediately.

## User Stories

1. As an operator, I want to invoke the program with the log source directory, the target local date, and the output SQLite database path as three CLI arguments, so that I can run today's batch or reprocess any historical day on demand.
2. As an operator, I want the file-discovery step to find the correct log file(s) for a target local date automatically, so that I don't need to know which numeric site-ID files exist on any given day.
3. As an operator, I want file discovery to correctly include the UTC-adjacent log file needed to fully cover a local day (based on the sign of the configured time-zone offset), so that hits near local midnight are never silently dropped or double-counted.
4. As an operator, I want the program to fail loudly with a clear "no files found" message and a non-zero exit code when no log files exist for the required date(s), so that a broken path or missing log delivery is caught immediately instead of silently producing an empty result.
5. As a GIS analyst, I want raw IIS log lines to never be persisted, only aggregate rows, so that the database stays small and doesn't retain excess traffic detail.
6. As a GIS analyst, I want each day's aggregate batch to fully replace any previous aggregate rows for that same local date, so that re-running a day never produces duplicated or doubled totals.
7. As a GIS analyst, I want the daily replace to happen atomically across all seven tables in one transaction, so that a crash mid-run never leaves a day half-updated.
8. As a GIS analyst, I want aggregated hit counts and total time taken by URI/endpoint, so that I can identify the busiest and slowest endpoints per day.
9. As a GIS analyst, I want aggregated hit counts and time taken by root path, so that I can see traffic distribution across top-level sites/applications.
10. As a GIS analyst, I want aggregated hit counts and time taken by user agent, so that I can understand which clients (browsers, ArcGIS Pro, scripts) are driving load.
11. As a GIS analyst, I want aggregated hit counts and time taken by referer, so that I can see which external sites or applications are driving traffic.
12. As a GIS analyst, I want aggregated hit counts and time taken by forwarded-for client IP, so that I can identify which real client IPs (behind a proxy/load balancer) are generating load.
13. As a GIS analyst, I want aggregated hit counts and time taken by the combination of referer and URI, so that I can see which specific pages/apps are driving traffic to which specific endpoints.
14. As a GIS analyst, I want aggregated hits, successful hits, failed hits, and time taken per ArcGIS Server service (site, folder, service name, service type), so that I can monitor the health and load of each published GIS service independently of unrelated Portal/admin traffic.
15. As a GIS analyst, I want ArcGIS admin (`/site/admin/*`) and Portal (`/portal/*`) traffic excluded from the ArcGIS-service aggregate, so that internal/administrative calls don't pollute service-usage metrics.
16. As a GIS analyst, I want a request that merely contains "rest" somewhere in its path or query string to NOT be miscounted as a real ArcGIS REST service call, so that the service aggregate only reflects genuine `/site/rest/services/...` requests.
17. As a developer, I want every log line's fields resolved by name from that file's own most-recently-seen `#Fields` header line, rather than assumed fixed positions, so that the parser stays correct even though field order/count has changed over the deployment's history (confirmed 16-vs-18-field drift in the real corpus).
18. As a developer, I want a header block that's missing a field required for aggregation to cause the entire physical file to be skipped, so that partially-schemed files never produce silently incomplete or misattributed aggregates.
19. As a developer, I want a data line whose field count doesn't match its governing header block's declared count to be skipped individually, so that one malformed line doesn't lose an otherwise-good file's data.
20. As an operator, I want an end-of-run summary reporting total lines read, valid-line count, invalid/skipped-line count, and elapsed processing time, so that I can sanity-check a run at a glance without digging into log files.
21. As an on-call engineer, I want the program to log to both console and a rolling file under a configurable `Logs` directory, so that I can review what happened on a scheduled run where console output wasn't captured.
22. As an on-call engineer, I want the log file to roll over at 10 MB and retain the last 10 files, so that historical run diagnostics are available without unbounded disk growth.
23. As an on-call engineer, I want every log statement produced while processing a given raw line to carry a `{filename}:{line-number}` correlation ID, so that I can trace any warning or error straight back to the exact source line that caused it.
24. As an on-call engineer, I want `Microsoft.*`/framework log namespaces pinned at `Error` while the application's own code logs at `Warning` by default and `Debug` in the Development environment, so that logs stay signal-heavy without needing a recompile to get verbose output for an investigation.
25. As a developer, I want every logging-capable class to accept an optional `ILoggerFactory` that falls back to a null logger when omitted, so that unit tests can construct any class without configuring a logging provider.
26. As an operator, I want the local time zone used for `local_date`/`local_date_time` derivation to be configurable via `appsettings.json` (using a value .NET's `TimeZoneInfo` understands), so that the same program can be deployed against logs from any IIS server regardless of its local time zone.
27. As a developer, I want the log source directory defaults, output paths, and log file location to be configurable via `appsettings.json` with a `Development` environment override, so that local development and production runs can use different settings without code changes.
28. As a developer, I want the seven aggregate tables created idempotently (`CREATE TABLE IF NOT EXISTS`) at startup, so that a fresh database file is usable immediately with no separate migration step for this fixed schema.
29. As a developer, I want CRUD for each aggregate table encapsulated in a dedicated Repository, and any non-CRUD/reporting queries kept in separate Query classes, so that repositories stay scoped to the entity they own as reporting needs grow.
30. As a developer, I want the parsing/normalization/aggregation logic to have zero database or filesystem dependencies, so that it can be exhaustively unit-tested against synthetic fixtures without any I/O.
31. As a developer, I want a synthetic, checked-in fixture suite covering the positive and negative case of every parsing rule (field-count mismatch, missing required field in a header block, ArcGIS service paths with/without a folder, admin/portal exclusion including the "contains rest but isn't a service call" case, empty/`-`/opaque non-URL referer values, `+`-encoded fields, multi-value X-Forwarded-For), so that the test suite stays valid even if the real sample log corpus changes or disappears.
32. As a developer, I want a separate regression test suite that runs the actual compiled console application against the full real-world `2026/` log corpus (including its schema drift, multi-header-block files, and rotating site IDs) and asserts on the resulting database contents, so that the implementation is proven correct against real, messy production data, not just clean synthetic cases.
33. As a developer, I want the solution split into a Domain project (pure parsing/aggregation logic), a Data project (SQLite schema, Repositories, Query classes), and a Console host project (composition root: CLI parsing, config, logging, wiring), so that each concern can be developed, reasoned about, and tested independently.
34. As a developer, I want every class in `src/` mirrored by a matching test class in the corresponding `tests/` project, so that coverage gaps are visible just by comparing the two trees.
35. As a developer, I want CLI argument parsing handled by the `CommandLineParser` package rather than hand-rolled or a preview-status package, so that argument handling is well-tested and low-maintenance.
36. As a developer, I want the SQLite driver to be `Microsoft.Data.Sqlite` and all SQL executed via Dapper (no ORM/change-tracking), so that the fixed, replace-oriented schema stays simple and the SQL executed is explicit and easy to reason about.
37. As a GIS analyst, I want `time-taken` values (recorded in milliseconds in the raw logs) converted to seconds and accumulated per aggregate group, so that the `time_taken_second` totals are directly comparable across aggregates without unit confusion.
38. As a GIS analyst, I want each aggregate row's `hits` count to always equal the number of matching log lines for that group (and, for the ArcGIS-service aggregate, `successful_hits + failed_hits` to always equal `hits`), so that the totals are internally consistent and trustworthy for reporting.

## Implementation Decisions

- **Language/runtime**: C# / .NET. The repo's `init-csharp-project` analyzer baseline (NetAnalyzers, VS Threading Analyzers, StyleCop, CleanCoders.Analyzers) is already applied at the root and covers every project created under `src/`/`tests/` automatically.
- **Solution layout**: one solution. `src/` holds three projects — the console host (root namespace `IisLogParserArcGIS`), `IisLogParserArcGIS.Domain`, and `IisLogParserArcGIS.Data`. `tests/` holds one mirrored xUnit project per `src/` project (`IisLogParserArcGIS.Tests`, `IisLogParserArcGIS.Domain.Tests`, `IisLogParserArcGIS.Data.Tests`, each 1:1 class-to-test-class) plus a separate `IisLogParserArcGIS.RegressionTests` project that intentionally sits outside that mirror (ADR 0004).
- **CLI**: the console host takes three required positional arguments — log source directory, target local date, output SQLite database path — parsed via the `CommandLineParser` package.
- **Configuration**: `Microsoft.Extensions.Configuration` reading `appsettings.json` with an `appsettings.Development.json` overlay. Configured values: local time zone (a `TimeZoneInfo`-compatible ID string), log output directory (default `.\Logs\` next to the executable), and application log level (`Warning` by default, `Debug` under the Development overlay); `Microsoft.*` namespaces stay pinned at `Error` regardless of environment.
- **File discovery** (Domain computes *which* dates; Host performs the actual glob): given a target local date and the configured offset, a pure Domain function determines which UTC calendar date(s) are needed — the target date, plus the UTC-adjacent date on whichever side the offset's sign requires (day-after for a negative/behind-UTC offset, day-before for positive, none for zero). The Host then globs the configured source directory for `u_ex<YYMMDD>*.log` for each needed UTC date, treating everything after the date as one opaque wildcard (ticket 16): the `_x_<siteId>` suffix seen in this deployment's corpus is that deployment's own naming choice, not a general IIS convention, and the program never detects, parses, or branches on it — a file's schema comes only from its own `#Fields` header.
- **Parsing pipeline** (Domain): the reader tracks the most recently seen `#Fields` header line per file (a file may contain multiple header blocks, e.g. after an IIS logging restart mid-day) and resolves every field by name from that header, never by a hard-coded position. A header block missing a field required by any aggregate causes the entire physical file to be skipped, with a logged reason. A data line is parsed only if its whitespace-split field count matches its governing header block's declared count; a non-matching line is skipped individually. Each valid line is normalized into a shared request model — deriving `utc_date_time` from the `date`+`time` fields, `local_date_time` via the configured time zone, and `local_date` as the grouping key — before being fed to all seven aggregate computations.
- **Aggregate computations** (Domain): implement the seven rules exactly as specified in `requirements.md` — by URI (`uri_stem` normalization, 1024-char truncation), by root (first path segment, lowercased, 16-char truncation, `-` fallback), by user agent (`+`→space, lowercase, 1024-char truncation), by referer (`-`/empty passthrough, `+`→space, lowercase, 4096-char truncation, opaque non-URL values such as internal Java class names accepted as-is), by forwarded-for IP (first IP from a comma/colon-separated, possibly `+`-encoded list, validated as an IP address, loopback placeholder when absent, 48-char truncation), by referer+URI (composed from the other two normalizations), and by ArcGIS Server service (site/folder/service_name/service_type parsed from `/site/rest/services/...`, folder optional, admin/portal paths excluded by path-segment check rather than substring match on "rest", trailing operation segment ignored, `successful_hits`/`failed_hits` split at `sc-status < 400`). `time-taken` converts from milliseconds to seconds and accumulates per group; `hits` increments per matching line.
- **Persistence** (Data): SQLite via `Microsoft.Data.Sqlite`, schema created idempotently with `CREATE TABLE IF NOT EXISTS` for the seven tables at startup — no migration framework. Dapper executes all SQL. Each aggregate table has a dedicated Repository handling its CRUD; cross-cutting/non-CRUD queries live in separate Query classes outside the repositories (ADR 0002). A day's batch replace is one transaction per run: delete existing rows for the target `local_date` across all seven tables, then insert the freshly computed rows, committed together so a failure never leaves a partially-replaced day.
- **Logging** (Host, used throughout): Serilog, writing to console and a rolling file under the configured `Logs` directory (10 MB rollover, last 10 files retained), one line of plain templated text per event (no JSON). Every logging-capable class across all three projects accepts an optional `ILoggerFactory` constructor parameter, falling back to `NullLoggerFactory.Instance` when omitted (ADR 0003). A correlation ID of `{filename}:{line-number}` is pushed into Serilog's context for the duration of processing each raw log line.
- **Run reporting** (Host): at the end of a run, the program prints a summary — total lines read, valid-line count, invalid/skipped-line count, and elapsed processing time. Zero log files found for the required date(s) is a hard failure: a clear "no files found" message and a non-zero exit code.

## Testing Decisions

- Tests assert on external behavior (inputs → observable outputs) only — never on internal implementation details — per the seams agreed for this feature.
- **`IisLogParserArcGIS.Domain.Tests`**: exercises the parsing/normalization pipeline and all seven aggregate rules directly, in-process, against small synthetic log-line fixtures checked into the test project — covering each rule's positive and negative/edge case (field-count mismatch, missing required field in a header block, both foldered and folderless ArcGIS service URLs, admin/portal exclusion including the "contains rest but isn't a service call" case, empty/`-`/opaque-string referer values, `+`-encoded fields, multi-value X-Forwarded-For). No filesystem or database access in this project.
- **`IisLogParserArcGIS.Data.Tests`**: exercises the Repositories and Query classes directly against a real (temporary-file) SQLite database — verifying idempotent schema creation, that a day's replace is genuinely transactional (a simulated failure mid-replace leaves the prior day's rows untouched), and that persisted `hits`/`successful_hits`/`failed_hits` values are internally consistent.
- **`IisLogParserArcGIS.Tests`** (mirrors the console host): covers Host-specific logic not already exercised by the other two suites — CLI argument validation/error messages and configuration binding.
- **`IisLogParserArcGIS.RegressionTests`**: invokes the actual compiled console executable against the real `2026/` log corpus (or a representative subset spanning its known schema drift, multi-header files, and site-ID rotation) with real CLI arguments and a temporary SQLite output path, then asserts purely on external behavior — process exit code, the end-of-run summary text on stdout, and the resulting rows queried directly from the output database. This is the highest-value seam for the feature as a whole; it treats the shipped artifact as a black box.
- Prior art: none — this is a fresh repository, so this test structure establishes the pattern (mirrored per-project unit tests plus one separate end-to-end regression project) that ADR 0004 expects future features to follow.

## Out of Scope

- Any UI/dashboard/reporting layer that consumes the aggregate tables — this spec covers only producing them.
- Retention/archival policy for old aggregate rows or old raw log files.
- Historical backfill orchestration beyond the single explicit-date CLI argument (e.g. a "process the last N days" wrapper) — a single run processes exactly one local date; backfilling a range is an operational concern for whatever calls this program, not this program's responsibility.
- Alerting/notification on run failure (e.g. emailing on a non-zero exit code) — the program's contract stops at exit code + logs.
- Multi-machine/distributed execution or concurrent runs against the same output database — the design assumes a single run at a time against a given SQLite file.
- Any change to how IIS itself is configured or how it produces log files.
