# 04 — Parsing & normalization pipeline

**What to build:** Raw lines from the discovered files become normalized, in-memory request records ready for aggregation — the parsing core every aggregate ticket will consume.

**Blocked by:** 03

**Status:** done

- [x] The reader tracks the most recently seen `#Fields` header line per file, supporting multiple header blocks within one file
- [x] Every field is resolved by name from the governing header, never by fixed position
- [x] A header block missing a field required by any aggregate causes the entire physical file to be skipped, with a logged reason
- [x] A data line whose field count doesn't match its governing header's declared count is skipped individually, without affecting the rest of the file
- [x] Each valid line is normalized into a shared request model carrying `utc_date_time`, `local_date_time`, and `local_date`
- [x] Every log statement emitted while processing a line carries a `{filename}:{line-number}` correlation ID
- [x] `Domain.Tests` cover, against synthetic fixtures: field-count mismatch, missing required field in a header block, and multiple header blocks in one file
- [x] Running the host against the real corpus reports plausible valid/invalid line counts (full summary formatting lands in ticket 14)

## Comments

Implemented as a Domain/Host split, matching ticket 03's pattern.

- **Domain** (`IisLogParserArcGIS.Domain/Parsing/`): `RequiredLogFieldNames` is the single source of truth for the 8 W3C field names (`date`, `time`, `cs-uri-stem`, `cs(User-Agent)`, `cs(Referer)`, `sc-status`, `time-taken`, `X-Forwarded-For`) that at least one of the seven aggregates needs — every other real-corpus field (`s-ip`, `cs-method`, `cs-uri-query`, `s-port`, `cs-username`, `c-ip`, `sc-substatus`, `sc-win32-status`, `sc-bytes`, `cs-bytes`) is read but never required. `LogFieldIndex` resolves a header's declared field names (case-insensitive) to column positions; `LogFieldsHeaderParser` recognizes `#Fields:` lines; `LogLineParser.Parse` turns one data line + governing `LogFieldIndex` + configured UTC offset into a `LogLineParseOutcome` (success/failure, not a bool+out pattern - see below); `LogFileParser.Parse` is "the reader" - it first scans every header block in the file to decide up front whether the whole file must be skipped (any missing required field, or no header at all), then does a single pass resolving each data line against its most-recently-seen header, closing over the file name and offset in a local function so per-line logging carries the `{filename}:{line-number}` correlation ID without threading them through as extra parameters.
- Field-specific normalization (case folding, `+`-decoding, truncation, IP/service-path parsing) is deliberately **not** done here - `NormalizedLogRequest` carries raw field strings (only `utc_date_time`/`local_date_time`/`local_date`, `sc-status`, and `time-taken` are actually parsed/typed) exactly as spec.md scopes it: those normalizations belong to each aggregate's own computation in tickets 06-12, not to the shared parsing pipeline.
- **Host** (`IisLogParserArcGIS/Parsing/LogCorpusParser.cs`): reads each discovered file's lines from disk and delegates to `LogFileParser`, aggregating requests and `LogLineCounts` across the run; wired into `Program.cs` right after file discovery. Logs one Information-level summary line (`Parsed N file(s) (S skipped): T line(s) read, V valid, I invalid.`) - full formatted run-summary output is explicitly deferred to ticket 14.
- **CleanCoders.Analyzers compliance drove real design choices, not just cosmetics**: this repo's `cleancoders.json` caps every method/constructor at 3 arguments repo-wide. A conventional `bool TryParse(..., out Result, out string reason)` shape doesn't fit an 8-field record, so `LogLineParser.Parse` returns a `LogLineParseOutcome` object instead of a bool+outs; `NormalizedLogRequest`/`LogFileParseResult` use `required` init-only properties + object-initializer construction (implicit 0-arg constructor) instead of positional records; `LogFileParser`'s per-line helper is a local function closing over `fileName`/`localUtcOffset` rather than a private method taking both as extra parameters; related int counts are bundled into one `LogLineCounts(Total, Valid, Invalid)` record (with an `Add`/`operator +` pair, since CA2225 wants the friendly alternate) instead of three loose ints threaded through every signature.
- **A real bug caught by the Domain.Tests before it ever ran against real data**: the first version of `LogFileParser`'s main loop fed the already-tracked `currentFieldIndex` variable directly as the `out` parameter of the per-line `LogFieldsHeaderParser.TryParse` check (`... || LogFieldsHeaderParser.TryParse(line, out currentFieldIndex)`). `TryParse`'s contract requires setting its `out` param to `null` on every non-header line - which silently wiped the just-seen header the moment the very next (non-header) line was checked, so every line after the first header in a file was treated as "no header seen yet". `Parse_IgnoresBlankAndCommentLines` and three other synthetic-fixture tests failed immediately with 0 requests where 1-2 were expected, which is exactly what caught it before the real-corpus smoke test ever ran. Fixed by only writing to `currentFieldIndex` on `TryParse`'s success branch.
- **Code review caught two further gaps**, both fixed before commit: (1) `LogCorpusParser.Parse` called `File.ReadAllLines` with no per-file exception handling, so one locked/deleted file would abort the whole day's run instead of being skipped like a bad header - now caught and logged the same way a bad header is, incrementing `SkippedFileCount` and continuing with the remaining files; (2) this also resolved a second finding about `Program.cs`'s shared catch block misattributing that same failure as "Failed to initialize configuration or logging" - fixing (1) means that specific exception no longer reaches that catch block at all. A third finding (the file parser does two full passes over each file's lines - one to validate every header block up front, one to actually parse) was left as-is: real corpus files run ~2,000 data lines/day, so the constant-factor doubling this avoids is negligible next to the correctness/clarity benefit of validating every header before committing to parsing any of them.
- Verified manually against the real `2026/` corpus (`DOTNET_ENVIRONMENT=Development`): `2026-05-01` (4 files, single header each) and `2026-06-08`/`2026-06-17` (files with 6 and 9 header blocks respectively, confirmed via `grep -c "^#Fields:"`) all report `0 invalid` with line counts matching `grep -vc '^#'` on the raw files exactly; spot-checked ten more dates spread across the year with the same result. No exceptions anywhere in the real corpus.
- `dotnet build` on the full solution: 0 warnings, 0 errors. `dotnet test`: 73 passed (29 Domain, 44 Host).
