# 18 — Portal item aggregate (`aggregated_by_portal_item`)

**What to build:** An eighth aggregate table, `aggregated_by_portal_item`, following the same principle as `aggregated_by_arcgis_service`: one row per distinct ArcGIS Portal item accessed on a local date, holding accumulated hits (split successful/failed by `sc-status < 400`, like the ArcGIS service aggregate) and time-taken. The identity is parsed from `cs-uri-stem` — a request is a portal item request if its path is shaped like the Portal Sharing REST API's item-access endpoints, under any of three URL shapes, keyed only on the item ID (username, folder ID, and the specific sub-resource/operation requested are read structurally but are not part of the identity).

**Status:** done

- [x] New Domain parser `PortalItemIdentityParser` (mirroring `ArcGisServiceIdentityParser`'s segment-based, case-insensitive, non-regex approach — split on `/`, structural position checks, no regex) extracts a portal item ID from a `cs-uri-stem` matching any of:
  - `/<W>/sharing/rest/content/items/<id>[/...]`
  - `/<W>/sharing/rest/content/users/<username>/items/<id>[/...]`
  - `/<W>/sharing/rest/content/users/<username>/<folderId>/items/<id>[/...]`

  where `<W>` is the configured web adaptor name (case-insensitive match, consistent with every other structural segment check in this codebase). Anything else under `/<W>/sharing/rest/content/users/<username>/...` that doesn't have `items` at the position right after the username or right after one further segment (e.g. `deleteItems`, `shareItems`, or any other bulk/non-item-scoped operation) does not match — no id extracted, no false positive, no error.
- [x] The trailing suffix after `<id>` (`data`, `resources/styles/root.json`, `info/thumbnail/...`, `update`, `updateThumbnail`, `status`, etc.) is not part of the identity — every request against the same id counts toward the same row regardless of which sub-resource or operation was requested. Username and folder ID (when present in the URL) are read structurally only to locate where `items`/`<id>` sit — they are discarded, never part of the identity, never persisted.
- [x] `portal_item_id` is treated as an opaque string — no format/hex validation of its content — and truncated to 64 characters defensively, consistent with every other normalized text column in this schema (`uri_stem` 1024, `user_agent` 1024, `referer` 4096, `forwarded_for_ip` 48, `root` 16).
- [x] New config setting `PortalWebAdaptorName` on `AppSettings`, bound from `appsettings.json` and defaulting to `"portal"` via the same `Coalesce`-with-default idiom already used for `LocalTimeZone`/`LogOutputDirectory`/`LogLevel` in `AppConfigurationFactory`. Added explicitly to `appsettings.json` (the other three settings are all spelled out there too, even though they have code-level defaults). Read once in `Program.cs` and threaded down as a plain parameter: `ByPortalItemAggregator.Aggregate(requests, localDate, portalWebAdaptorName)` → `PortalItemIdentityParser.TryParse(uriStem, portalWebAdaptorName, out portalItemId)` — keeping the Domain layer decoupled from config-loading infrastructure, the same reasoning behind Domain code receiving an already-resolved `TimeSpan` UTC offset rather than a raw time zone ID string.
- [x] New aggregate table `aggregated_by_portal_item`, matching `aggregated_by_arcgis_service`'s column shape exactly except for the single-field identity:
  ```sql
  CREATE TABLE IF NOT EXISTS aggregated_by_portal_item (
      id INTEGER PRIMARY KEY,
      local_date TEXT NOT NULL,
      portal_item_id TEXT NOT NULL,
      time_taken_second REAL NOT NULL,
      hits INTEGER NOT NULL,
      successful_hits INTEGER NOT NULL,
      failed_hits INTEGER NOT NULL
  );
  ```
  `successful_hits`/`failed_hits` split at `sc-status < 400`; `hits = successful_hits + failed_hits` always holds, exactly like the ArcGIS service aggregate's invariant.
- [x] `AggregateTableNames.All`, `AggregateDatabaseSchema`, `DailyAggregateBatch`, `DailyAggregateReplacer`, and `Program.cs` all gain the eighth aggregate/repository, following exactly the same wiring pattern used for the seventh (ArcGIS Server Service) at each of those sites.
- [x] `Domain.Tests` cover: all three matching URL shapes (bare item, user-scoped item, user+folder-scoped item); the bulk-operation shape that must NOT match (`deleteItems`/`shareItems`-style, and any other `content/users/<username>/<x>` where `<x>` isn't `items` and isn't followed by `items`); that a non-default configured web adaptor name (e.g. `"gis"`, not hardcoded to `"portal"`) is honored, not assumed; case-insensitive matching on every structural segment; the successful/failed hit split with the `hits = successful + failed` invariant; date filtering (other local dates ignored); null-argument guard.

## Comments

Raised while reviewing the real corpus's actual portal traffic (queried directly from the `2026.sqlite` output produced by ticket 17's backfill script, not just the sample the project owner had eyeballed first): the initially-described pattern (`/portal/sharing/rest/content/items/<id>[/...]`) only accounts for direct item access. The same corpus also has user-scoped item access (`content/users/<username>/items/<id>`, `content/users/<username>/<folderId>/items/<id>` — real ArcGIS Portal Sharing API shapes, items can be addressed directly or scoped under their owning user and an optional folder) and user-scoped bulk operations with no item ID in the URL at all (`deleteItems`, `shareItems` — IDs go in the POST body for those). Corpus volumes: 25,354 hits for the direct shape, 34 for the two user-scoped item shapes combined, 268 for the ID-less bulk operations (which must never be mistaken for carrying an ID). All three ID-bearing shapes are in scope; the ID-less shape must structurally fail to match, not error or produce a garbage ID.

Also raised: the literal string `"portal"` at the start of the path is this deployment's own Web Adaptor name, not a fixed ArcGIS Enterprise convention — a different installation could name it differently. Made configurable (`PortalWebAdaptorName`, default `"portal"`) rather than hardcoded, unlike `site`/`folder`/`service_name` in the ArcGIS service aggregate, which stay parsed-per-URL because an installation can have many ArcGIS Server sites simultaneously (this corpus alone has `mimas`, `titan`, `phobos`, `europa`, `arcgis`, `umbriel`, `charon`, `deimos`) but exactly one Portal deployment with one fixed Web Adaptor name.

`successful_hits`/`failed_hits` were added despite not being in the project owner's original five-column list, after confirming during grilling that the ArcGIS-service-style split was in fact wanted, not just a passing thought.
