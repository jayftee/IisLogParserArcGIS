# 19 — Split the CLI into `harvest` / `regenerate` / `harvest-regenerate` verbs

**What to build:** Today `IisLogParserArcGIS.exe <logSourceDirectory> <targetLocalDate> <outputDatabasePath>` always harvests one date's logs *and* regenerates the entire Dashboard, unconditionally, in that one invocation. That's wasteful for a backfill: `Invoke-IisLogBackfill.ps1` (ticket 17) calls the exe once per date in a backlog, so a full year's worth of dates triggers a full Dashboard rebuild after every single date when only the very last one's output matters. Replace the single implicit command with three explicit `CommandLineParser` verbs so harvesting and regenerating can be invoked independently.

**Status:** done

- [x] Split `ProgramArguments` into three verb types (`[Verb("harvest")]`, `[Verb("regenerate")]`, `[Verb("harvest-regenerate")]`), parsed via `parser.ParseArguments<HarvestArguments, RegenerateArguments, HarvestRegenerateArguments>(args)`. No default/implicit verb — an invocation with no verb, or an unrecognized one, falls through to `CommandLineParser`'s standard usage/help output and a non-zero exit code, exactly like an unrecognized verb does today in any other `CommandLineParser`-based tool.
  - `harvest <logSourceDirectory> <targetLocalDate> <outputDatabasePath>` — same three positional arguments as today's single command.
  - `regenerate <inputDatabasePath>` — one positional argument. Named `inputDatabasePath`, not `outputDatabasePath`, even though it's the same physical SQLite file `harvest` writes to — this verb only ever reads it.
  - `harvest-regenerate <logSourceDirectory> <targetLocalDate> <outputDatabasePath>` — today's exact combined behavior, unchanged argument shape, now its own named verb instead of the implicit default.
- [x] `Program.cs` dispatches on the parsed verb:
  - `harvest` runs today's discover → parse → aggregate → `DailyAggregateReplacer.Replace` path and stops — it must not call `RegenerationRun.Run` at all.
  - `regenerate` opens the database at `inputDatabasePath`, builds configuration exactly as today, and calls `RegenerationRun.Run` directly — it must not touch log discovery, parsing, or aggregation.
  - `harvest-regenerate` keeps today's exact combined sequence.
- [x] Argument validation (`CliArgumentValidator` or its per-verb equivalent) validates only the arguments each verb actually declares — `regenerate` validates just `inputDatabasePath` as a path; it never sees or requires `logSourceDirectory`/`targetLocalDate`.
- [x] `CONTEXT.md`: add a new **Harvest Run** entry and reword the existing **Regeneration Run** entry, per the wording agreed during grilling (see Comments) — both entries stand alone and cross-reference each other by name; neither mentions CLI verb names, matching every other entry in the file.
- [x] `README.md`: the "Run" section documents all three verbs and their arguments, and calls out which one an operator reaches for day-to-day (`harvest-regenerate`, for a routine single-date run) versus during a backfill (`harvest` per date, `regenerate` once at the end).
- [x] `Invoke-IisLogBackfill.ps1` (ticket 17): the per-date loop now invokes the exe with the `harvest` verb instead of the old bare invocation. After the loop finishes, invoke the exe once more with `regenerate <OutputDatabasePath>` — **unconditionally**, regardless of how many dates succeeded or failed, including a run where every date failed (the script has no way to know whether the Dashboard was ever generated before this run, so skipping regeneration on an all-failure run was considered and rejected).
- [x] New ADR under `docs/adr/` capturing the explicit-verbs, no-default-verb decision: hard to reverse (the backfill script and the Task Scheduler deployment both depend on the invocation shape), not obvious to a future reader (why is there no bare-invocation fallback for backward compatibility?), and a genuine trade-off (explicitness over backward compatibility, justified by this being an internal tool with effectively one real caller).
- [x] Existing tests updated for the new shape: `CliArgumentValidatorTests` / `ProgramArguments`-related tests split or duplicated per verb; any regression or end-to-end test that invokes the compiled exe with today's bare 3-positional-argument syntax updated to use `harvest-regenerate` (or `harvest`, wherever the test doesn't care about the Dashboard).

## Comments

Raised while investigating a ~922,000,000-record backfill over a full year of real corpus data: every one of ~365 per-date CLI invocations was triggering a full Dashboard rebuild, when only the very last one's output actually matters.

Design decisions from grilling, for context:

- **`CommandLineParser` verbs, not boolean flags on the existing single command, and no implicit default verb.** This is an internal ops tool with effectively one real caller (the backfill script) plus occasional manual runs, so backward compatibility bought little, while explicit verbs mean every invocation states its own intent and each mode gets exactly the argument list it actually uses. Critically, a flag-based design (`--skip-dashboard`, `--dashboard-only`) would have forced `regenerate` to accept — or the parser to require — a meaningless `logSourceDirectory`/`targetLocalDate`, since `CommandLineParser` ties positional values to one fixed argument shape regardless of flags.
- **`regenerate`, not `dashboard`, as the dashboard-only verb name** — kept traceable to the existing `CONTEXT.md` term "Regeneration Run" rather than introducing "dashboard" as a second, competing name for the same concept ("Dashboard" already names the generated site itself).
- **`regenerate`'s argument is `inputDatabasePath`, deliberately asymmetric with `harvest`'s `outputDatabasePath`** — same physical file, but reusing "output" for a read-only verb would have been misleading.
- **`CONTEXT.md`'s Harvest Run / Regeneration Run entries were written to stand alone**, not as "before/after steps of one bigger operation" — Regeneration Run in particular predates this ticket and was originally only ever triggered automatically as the tail end of a combined run; its wording is updated to reflect that it's independently triggerable, operating on whatever the aggregate database currently holds, regardless of what produced those contents or when.
- **The backfill script's final `regenerate` call is unconditional**, even on an all-failure run — the "skip it when nothing changed" optimization was considered and explicitly rejected, since the script can't know whether the Dashboard was ever generated by a prior run.

Full grilling transcript covered: selection mechanism (verbs vs. flags), backward-compatibility trade-off, verb naming, the `regenerate` argument's name, the backfill script's zero-success edge case, and the `CONTEXT.md` wording for both entries.

## Comments

Implemented as scoped:

- `ProgramArguments`/`CliArgumentValidator`'s old single-command shape is gone. `HarvestArguments` and `HarvestRegenerateArguments` both derive from a new `HarvestArgumentsBase` (implementing `IHarvestArguments`) that declares the three shared `[Value]`-attributed positional properties exactly once — `CommandLineParser` binds attributes on inherited properties correctly, confirmed live via `harvest --help`, so the two verbs cannot drift apart in their declared CLI surface. `RegenerateArguments` is its own type with the single `inputDatabasePath` positional. `CliArgumentValidator` gained a `Validate(IHarvestArguments)` overload (unchanged logic, renamed parameter type) and a new `Validate(RegenerateArguments)` overload.
- `Program.cs` restructured into `RunHarvest(IHarvestArguments, bool alsoRegenerate)`, `RunRegenerate(RegenerateArguments)`, and a shared `RegenerateDashboard(SqliteConnection, IConfiguration)` used by both the `regenerate` path and `harvest-regenerate`'s tail end. `harvest` never builds `ReportsSettings` or calls `RegenerationRun.Run`; `regenerate` never touches `LogFileLocator`/`LogCorpusParser`/aggregation and doesn't bind `AppSettings` at all, since `RegenerationRun.Run` only needs `ReportsSettings` (which carries its own `LocalTimeZone`, bound independently from the same shared `appsettings.json`).
- Code review (run before this commit, findings addressed below) caught that `regenerate` would silently create a brand-new, empty aggregate database and exit 0 if `inputDatabasePath` didn't exist (`SqliteConnectionFactory.Open` creates the file). Fixed: `CliArgumentValidator.Validate(RegenerateArguments)` now throws a `CliArgumentValidationException` when the path doesn't exist, with a message naming the verb's read-only contract. Verified live: `regenerate <nonexistent path>` now exits 1 with a clear stderr message instead of publishing an empty Dashboard over a real one.
- Test coverage: `CliArgumentValidatorTests` extended with `harvest-regenerate` coverage, the `regenerate` happy path (against a real temp file, since existence is now enforced), and the new non-existent-path rejection. `HarvestedAggregateDatabaseFixture` and `CompiledProgram.RunAsync` (both in the test suites) switched to invoke `harvest` instead of the old bare/combined invocation, since neither ever asserted on Dashboard output — confirmed via `ProcessRunner`'s remaining comment, updated to describe the real shared side effect (the rolling log file, not the Dashboard).
- Verified live against the real `2026/` corpus: `harvest` for 2026-01-01 exits 0 and does **not** create a `Dashboard` folder; a subsequent standalone `regenerate` against that same database exits 0 and **does** create it. `harvest --help`/`regenerate --help`/`harvest-regenerate --help`/bare `--help` all render correctly through the verb-based parser.
- Full fast suites green: `IisLogParserArcGIS.Domain.Tests` (164), `IisLogParserArcGIS.Data.Tests` (121), `IisLogParserArcGIS.Tests` (56, up from 55). `IisLogParserArcGIS.RegressionTests` and `IisLogParserArcGIS.Reports.Tests` were run and have real failures, but both were confirmed (by stashing this ticket's changes and re-running against unmodified `main`) to fail identically on the pre-existing baseline, unrelated to this ticket:
  - `RegressionTests`' three schema/multi-header/site-rotation tests fail on an exact-double line-count mismatch (e.g. expected 1992, actual 3984) on both baseline and this branch — a pre-existing parsing/counting bug, not touched by this ticket's CLI-only changes.
  - `Reports.Tests`' `HarvestedAggregateDatabaseFixture` fails partway through building its shared fixture database, on both a `harvest`-only build (this branch, fails late in the corpus's date range on a real UTC-adjacent-file boundary gap) and a `harvest-regenerate`-equivalent build (baseline, fails earlier with a Dashboard-file locking collision) — traced to the prior commit's `LocalTimeZone: America/Edmonton` change (a negative UTC offset now requires an adjacent-day file the corpus's last date doesn't have) interacting with this fixture's full-date-range discovery; not caused by this ticket, and this ticket's `harvest`-only fixture build is, if anything, less exposed to the baseline's Dashboard-file contention.
  Both are pre-existing and out of scope for this ticket, same treatment ticket 18 gave its own unrelated pre-existing flake.
