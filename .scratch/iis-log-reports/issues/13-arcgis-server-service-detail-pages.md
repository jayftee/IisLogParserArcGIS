# 13 — ArcGIS Server service Detail Pages

**What to build:** A Detail Page for any individual service, reachable only by clicking its row in the ArcGIS Server Complete View (ticket 12) — nothing else links to one — showing that service's own request-volume and average-processing-time evolution (successful and failed), with an in-page All/Last-7-Days toggle since it isn't a bookmarked sidebar destination.

**Blocked by:** 12.

**Status:** done

- [x] Detail Page is generated for every service in the aggregate database under an Included Root, linked only from the Complete View.
- [x] Each of the service's 4 line charts (success/fail count, success/fail average time) spans only the real date range the service has data for — no zero-padding before its first appearance or after its last (verified with a fixture-injected sparse-data service, per ticket 09's edge-case helper).
- [x] In-page toggle switches between All and Last 7 Days without navigating to a different page.

## Comments

New Data-project queries `ByArcGisServiceDetailDailyHitTotalsQuery`/`ByArcGisServiceDetailDailyAverageTimeQuery` (`src/IisLogParserArcGIS.Data/Queries/`) mirror the existing per-site daily queries but filter on a full `ArcGisServiceIdentity` (site, folder — matched null-safely via SQLite's `IS` operator, service name, type) instead of just `site`, reusing the identical `ByArcGisServiceDailyHitTotalRow`/`ByArcGisServiceDailyAverageTimeRow` row shapes. No SQL view: the tuple is already the base table's own grain, so per ticket 03's resolution there's nothing left to collapse across.

`ArcGisServiceDetailPageBuilder` (`src/IisLogParserArcGIS.Reports/Sections/`) drives its page set from `ByArcGisServiceRangeTotalsQuery` — the exact same calendar-year-to-date, Included-Root-filtered rows ticket 12's Complete View lists, since a Detail Page is reachable only from there. Each page embeds both All and Last 7 Days ranges at once: the All range's 4 charts draw immediately, while the Last 7 Days range's charts sit inertly inside a `<template>` and are only cloned into a live panel (and thus only drawn) on the toggle's first click — avoiding the alternative of drawing a Google Chart into a hidden, zero-size container. Wired into `RegenerationRun.Run` after the Complete View; `DashboardSidebar.ArcGisServiceDetailHref` computes each page's URL but is deliberately never added to `BuildTree`, so no sidebar entry ever points to one.

`ArcGisServerCompleteViewBuilder` (ticket 12) now links each row's Service Name to its Detail Page, using Google Charts' `{v, f}` formatted-cell shape so the column still sorts by the plain name rather than by the link markup. This needed two small `Rendering` additions: `TableCellContent` (an `allowHtml` toggle for `RenderTable`, mirroring `TablePaging`'s enum style) and `RelativeLinkHelper` (the "../" prefix logic extracted out of `PageShellRenderer` so a section builder can compute a correct relative link from its own page to another page's root-relative href). `ArcGisServerChartBodies`'s two chart-body builders gained an explicit `elementId` parameter (previously computed internally) since a Detail Page needs two distinct ids per metric - one per range - on the same page; `ArcGisServerSectionBuilder`'s call sites were updated to pass the exact same literal ids as before, a verified no-op. `ArcGisServerLeaderboardBodies`'s private label formatter was extracted to the shared `ArcGisServiceLabelFormatter`, now reused by the Detail Page's own title.

Test coverage: `ByArcGisServiceDetailDailyHitTotalsQueryTests`/`ByArcGisServiceDetailDailyAverageTimeQueryTests` (folder null-safety, cross-service exclusion, date-range filtering, empty/null cases) in `Data.Tests`; `ArcGisServiceDetailPageTests` in `Reports.Tests` drives `RegenerationRun.Run` end-to-end against the ticket-09 harvested fixture and asserts a page exists for every service the Complete View lists, no sidebar entry ever links to one, exactly one file exists per service (proving the toggle stays in-page), and — using `WorkingDatabaseCopy` to inject a service with hits on only two widely-separated dates — that its chart shows exactly those two dates with no zero-padded dates in between. `ArcGisServerCompleteViewTests` was updated to parse the embedded chart JSON and assert on decoded cell values (site/folder/type/hits, plus the Service Name cell's `v`/`f` split) rather than matching literal escaped substrings, decoupling it from `JsonSerializer`'s own escaping choice. Full suite green: 164 Domain.Tests, 84 Data.Tests, 48 Cli Tests, 4 RegressionTests, 46 Reports.Tests (346 total).

Reviewed via `/code-review` against `HEAD`. Fixed: a class-wide switch to `JavaScriptEncoder.UnsafeRelaxedJsonEscaping` (meant to make the one new link cell's markup readable in the generated static file) had silently disabled `<`/`>` escaping for every chart's JSON on every page - a real stored-XSS opening, since folder/service/type names are unvalidated URI segments and the Dashboard has no auth (ADR-0006); reverted to the default safe encoder everywhere, since a JS engine reads `\uXXXX` escapes identically to the literal characters. Also fixed: the Service Name cell's sort-by-markup regression (via the `{v, f}` cell shape above), and the toggle's ad hoc `"all"`/`"last7"` range identifiers (now reusing `DashboardDateRange` and the `"last-7-days"` slug already established by `ArcGisServerPageHref`). Deliberately not changed: Detail Pages are scoped to the same year-to-date/Included-Root set as the Complete View rather than literally every service ever recorded - a narrower but consistent reading, since "linked only from the Complete View" forces the same scope; and the new per-service queries duplicate their per-site siblings' SQL shape, matching this codebase's established preference (per ticket 03) for explicit small query classes over shared abstraction.
