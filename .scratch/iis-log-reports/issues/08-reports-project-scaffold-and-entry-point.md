# 08 — Reports project scaffold & Regeneration Run entry point

**What to build:** A new `IisLogParserArcGIS.Reports` project that runs immediately after the daily CLI import completes, reading the aggregate database and its own configuration, and successfully produces (or refreshes) an output directory — the scaffold every later ticket builds pages into. No report content yet; this ticket is the foundation.

**Blocked by:** None — can start immediately.

**Status:** done

- [x] New `IisLogParserArcGIS.Reports` project added to the solution, referencing `IisLogParserArcGIS.Data` (per [ADR-0002](../../../docs/adr/0002-dapper-repository-and-query-split.md)'s conventions).
- [x] Reports' own `appsettings.json` holds the Included Root allow-list (flat, lowercase array) and a new `PortalBaseUrl` setting.
- [x] A `TimeProvider` (the standard .NET abstraction, not a bespoke interface) is injected into the entry point; `yearStart` and `today` are computed once at Regeneration Run start (using the existing local-time-zone resolution) and available to thread through every later query.
- [x] The Regeneration Run is triggered immediately after the existing daily CLI import completes, with no independent schedule.
- [x] Running the entry point against a populated aggregate database and a given output directory completes successfully (exit code 0) and is safe to re-run — always replaces prior output, never merges or duplicates it.
- [x] No page-rendering or report-query logic yet — that starts in ticket 10.

## Comments

Implemented in `eb3bf27`: new `IisLogParserArcGIS.Reports` class library referencing `IisLogParserArcGIS.Data`, with its own `reports.appsettings.json`/`reports.appsettings.Development.json` (named distinctly from `appsettings.json` since the Cli calls into Reports in-process and both projects' config files land in the same output directory) holding `LocalTimeZone`, `IncludedRoots`, `PortalBaseUrl`, and `OutputDirectory`, bound via `ReportsConfigurationFactory`/`ReportsSettings`.

**Superseded**: the separate `reports.appsettings*.json` files were consolidated into the Cli project's own `appsettings.json`/`appsettings.Development.json` — since this is genuinely one executable that always harvests *and* regenerates the Dashboard together, on every run, two files (with `LocalTimeZone` duplicated, uncoupled, across both) was a real footgun rather than useful isolation. `ReportsConfigurationFactory` now only binds `ReportsSettings` from the `IConfiguration` `Program.cs` already built once for `AppSettings`; its own `Build` method (and the `Microsoft.Extensions.Configuration.Json` package it needed) was removed. See [README.md](../../../README.md#configuration). `RegenerationRunBoundaries.Resolve` derives `Today`/`YearStart` once from an injected `System.TimeProvider` and the configured local time zone (`TimeZoneInfo.ConvertTimeFromUtc`, not `LocalUtcOffsetResolver`'s local-date-based overload, since converting UTC→local doesn't have that method's DST ambiguity). `RegenerationRun.Run(connection, settings, timeProvider, outputDirectory)` is the primary seam (per spec.md): it resolves those boundaries, refuses an output directory that resolves to a drive root, and replaces the output directory outright (delete-if-exists, then recreate) so a rerun never merges with prior output. `Program.cs` now references the Reports project and calls `RegenerationRun.Run` immediately after `DailyAggregateReplacer.Replace` succeeds, resolving the configured (possibly relative) output directory via a new shared `RelativePathResolver` (extracted from `SerilogLoggerFactoryBuilder`, which had the identical logic) and refusing to let it resolve to the executable's own directory. Test coverage: `RegenerationRunBoundariesTests` (UTC/offset/year-boundary/invalid-timezone/null-argument cases), `RegenerationRunTests` (creates and re-creates the output directory without merging, returns the resolved boundaries, drive-root guard, null-argument guards, against a real schema-backed SQLite connection), and `ReportsConfigurationFactoryTests` (default/provided binding, Development overlay). Spot-checked end-to-end: running the compiled Cli exe against the real `2026/` corpus for one date exits 0 and produces a `Dashboard` directory next to the executable; rerunning it replaces rather than duplicates that output. Full suite green: 267 tests passing across all five test projects (19 of them new, in `IisLogParserArcGIS.Reports.Tests`).
