# 18 — Sanitize Detail Page path segments (folder/service name/type, Portal item id)

**What to build:** During a real production run, an operator observed a message during Dashboard creation pointing at a folder/service name containing an unusual character (a `*`) that broke file creation. `DashboardSidebar.ArcGisServiceDetailHref`/`PortalItemDetailHref` embed `folder`/`serviceName`/`serviceType` (ticket 13) and `portalItemId` (ticket 16) directly into Dashboard output-relative file paths with no filesystem-safety sanitization — only lowercased/truncated at the Domain layer, never checked for characters illegal in a Windows path. Unlike `site` (always an Included Root drawn from the operator's own curated allow-list), these four values are parsed straight from the request URI with no allow-list filtering, so a scanner or malformed request can put any character a URI path segment allows into one of them, crashing the whole Regeneration Run when `StaticPageWriter.Write`'s `Directory.CreateDirectory`/`File.WriteAllText` calls reject the resulting illegal path.

**Status:** done

- [x] New `DetailPagePathSegment.Sanitize(string)` in `IisLogParserArcGIS.Reports.Rendering`: replaces every character illegal in a Windows file/directory name with `_`, strips trailing dots/spaces (which Windows itself silently strips - left alone, two differently-spelled segments could quietly land on the same directory/file), and rejects an exact (case-insensitive, post-trim) match against a Windows-reserved device name (`CON`, `PRN`, `AUX`, `NUL`, `COM1`-`COM9`, `LPT1`-`LPT9`).
- [x] Whenever any of the above actually changes the value, a short deterministic suffix (FNV-1a hash of the *original* raw value, not the OS's randomized `string.GetHashCode()`) is appended, so two different raw values that would otherwise sanitize to the same result (e.g. `"item*1"` and `"item?1"`, both becoming `"item_1"`) can never silently overwrite each other's Detail Page. A value left untouched by every check - the overwhelming common case for real ArcGIS Server/Portal identifiers - is returned exactly as given, so no existing Detail Page's URL changes.
- [x] Wired into `DashboardSidebar.ArcGisServiceDetailHref` (folder/serviceName/serviceType, not site) and `DashboardSidebar.PortalItemDetailHref` (portalItemId) - the single choke point both `ArcGisServiceDetailPageBuilder`/`PortalItemDetailPageBuilder` (the file-writer) and every Complete View page that links to a Detail Page already go through, so the file actually written and every link pointing at it stay consistent automatically with no separate wiring.
- [x] New `DetailPagePathSegmentTests` (25 tests): every individual illegal character, control characters, ordinary values returned unchanged, empty input, `.`/`..`/`...`/all-space traversal segments, every reserved device name (case-insensitive), trailing-dot collision cases, determinism (same input twice), collision-avoidance (two different colliding raw inputs produce different results), null-argument guard.
- [x] New regression tests in `ArcGisServiceDetailPageTests`/`PortalItemDetailPageTests`: a service name/portal item id containing `*`/`?` inserted via `WorkingDatabaseCopy`, `RegenerationRun.Run` asserted to complete and write a sanitized (no `*`/`?`) Detail Page, following this file's existing edge-case-row testing convention exactly.

## Comments

Investigated after the project owner reported (without a saved screenshot) seeing a message during Dashboard creation related to characters - like a star - in a folder or service name breaking file creation. Traced to `DashboardSidebar`'s two Detail Page href builders having no sanitization at all, while `site` is implicitly safe only because it's filtered through the operator-curated `IncludedRoots` allow-list before any page is built for it - folder/serviceName/serviceType/portalItemId have no equivalent filter.

Code review (run twice) caught real gaps beyond the initially-reported `*` character, both fixed before commit:

- The first pass only replaced illegal punctuation/control characters, missing Windows-reserved device names (a folder or service type of exactly `con`, `nul`, etc. would still crash `Directory.CreateDirectory`/`File.WriteAllText` even with zero illegal characters) and the silent-overwrite risk of two different raw values sanitizing to the same result with no disambiguation.
- Fixed together via one mechanism: trailing dots/spaces are stripped (matching what Windows itself does silently) and reserved names are rejected outright: whenever any of this changes the value, a short deterministic hash suffix of the original raw value is appended, so colliding sanitized results (from illegal characters, reserved names, or trailing-dot stripping) always end up distinct. Ordinary values are completely unaffected - no suffix, byte-identical to before this ticket.

Verified live end-to-end (not just unit tests) with a throwaway scratch test driving the real `RegenerationRun.Run`: a service name of `weird*service?`, a folder/service name of exactly `con`, and a service *type* of `con` (the trailing segment before `.html`) all completed without throwing and produced a real Detail Page file, then the scratch test was deleted.

Full solution builds clean, 0 warnings. `Domain.Tests` (164), `Data.Tests` (121), and `Tests` (56) all pass unaffected. `Reports.Tests` gained 25 sanitizer unit tests (all passing) and 2 new fixture-dependent regression tests; the latter two can't currently execute in this environment because `HarvestedAggregateDatabaseFixture` already fails to build for an unrelated, pre-existing reason (documented in `.scratch/iis-log-parser/issues/19-cli-harvest-and-regenerate-verbs.md`'s Comments: the `LocalTimeZone: America/Edmonton` setting interacting with a real UTC-adjacent-file gap at the very end of the corpus's date range) - confirmed via the standalone scratch test instead, which needs no corpus fixture.

Closing: verified against a full production run over the 2026 IIS logs (smaller than 2025's ~922M requests, but still large-scale) - harvesting and Dashboard regeneration both completed with no path-related failures, confirming this fix holds under real corpus data, not just the scratch/unit tests above.
