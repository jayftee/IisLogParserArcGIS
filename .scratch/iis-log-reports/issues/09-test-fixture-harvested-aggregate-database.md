# 09 — Test fixture: harvested aggregate database from the 2026 corpus

**What to build:** A reusable test fixture for the Reports project's test suite that produces a realistic, multi-day, multi-entity aggregate database from real data — by replaying the existing `IisLogParserArcGIS.RegressionTests` project's own tooling once per date across the full checked-in `2026/` corpus into one shared SQLite file — instead of hand-typed fixture rows. Every later Reports ticket's tests consume this fixture rather than building their own.

**Blocked by:** None — can start immediately (prefactoring; can run in parallel with ticket 08).

**Status:** done

- [x] A shared fixture (built once per test collection, not once per test — this replays the shipped executable once per corpus date, so it's expensive) that calls the existing `CompiledProgram`/`TempOutputDatabase`-style tooling once per date across the full `2026/` corpus date range, into one shared output SQLite database file.
- [x] The resulting database contains the real Included Roots, the `proxy` Root, and a realistic spread of ArcGIS Server services and Portal Items — verified by at least one test asserting known entities are present.
- [x] A helper that inserts extra rows into a working copy of the harvested database, for edge cases the corpus doesn't naturally contain (an exact ranking tie between two entities; an entity that only appears for part of the date range).
- [x] Documented in the test project as the standard fixture strategy for this feature, so later tickets reuse it rather than re-deriving their own approach.

## Comments

Implemented in `58caba9`: `IisLogParserArcGIS.Reports.Tests/TestSupport/HarvestedAggregateDatabaseFixture.cs` is an `IAsyncLifetime` xUnit fixture that discovers the full inclusive date range of the checked-in `2026/` corpus from its file names (not just the dates that have a file of their own, since a `u_ex<date>` file can carry lines timestamped for the adjacent day) and replays `IisLogParserArcGIS.RegressionTests`'s own `CompiledProgram.RunAsync` once per date into one shared temp SQLite file — safe because a Daily Batch replace only ever touches its own date's rows. `HarvestedAggregateDatabaseCollection` (`[CollectionDefinition]`/`ICollectionFixture<...>`) builds it once per test run rather than per test class — the first xUnit collection fixture in this solution. The `RegressionTests` tooling is reused rather than duplicated via a new `ProjectReference` from `Reports.Tests` plus `[InternalsVisibleTo("IisLogParserArcGIS.Reports.Tests")]` on `RegressionTests`. Because the shipped executable also regenerates a shared Dashboard folder as a side effect of every run, `ProcessRunner.RunAsync` (the tooling both test projects funnel through) now serializes every invocation across processes behind a named `Mutex`, so this fixture and the `RegressionTests` suite can safely run concurrently. `WorkingDatabaseCopy` copies the harvested database to a private temp file and offers `InsertArcGisServiceRows`/`InsertPortalItemRows` (backed by the existing `ByArcGisServiceRepository`/`ByPortalItemRepository`) for edge-case rows, leaving the shared harvested file untouched. Test coverage: `HarvestedAggregateDatabaseFixtureTests` (all 14 real Included Roots present, the `proxy` Root present, ≥100 distinct ArcGIS services and Portal Items — the real corpus yields 917/1,079) and `WorkingDatabaseCopyTests` (an inserted exact-hit-count tie and a partial-date-range Portal Item, both visible only on the copy). The standard-fixture-strategy documentation lives as dense XML doc comments on the fixture, collection, and working-copy types, matching this repo's existing test-support convention. Full suite green across all six test projects.
