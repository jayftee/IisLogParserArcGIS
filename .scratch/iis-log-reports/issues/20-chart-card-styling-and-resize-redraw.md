## Comments

Scoping the card to `.chart` alone (not the whole content area) was deliberate: it's the one class already shared by every Google widget's own container, in every render method, on every kind of page (metric charts, Leaderboards, Complete View tables, Detail Page charts) - no HTML changes needed anywhere else, just this one CSS hook plus the new JS registration each render method already had a natural place to add.

Redraw is global-registry-based rather than per-chart `ResizeObserver`s because a single page can carry more than one chart at once - a Detail Page embeds both range variants (ticket 13/16's "both ranges, one page, in-page toggle") as two separate chart divs, both needing to repaint on resize even though only one is visible at a time.

Verified against the real 2026 corpus end-to-end: rebuilt the console host, ran `regenerate` against the aggregate database from ticket 19's full run, and confirmed the real generated `assets/dashboard.js`, the card CSS in `assets/site.css`, and `__dashboardCharts.push(redraw)` in an actual chart page's inline script all landed as expected. Solution builds clean, 0 warnings; `Domain.Tests` (164), `Data.Tests` (121), and `Tests` (56) still pass throughout every round below. `Reports.Tests` wasn't re-run for this ticket beyond the build - no test in that project asserts on `.chart`'s CSS or the chart scripts' exact JS, so there was nothing there to regress, and it still carries the same pre-existing, unrelated `HarvestedAggregateDatabaseFixture` failure documented in tickets 18/19.

The chart-fill-height work (fill the remaining space down to the footer) went through several rounds of visual feedback from the operator, and two of those rounds were guessed wrong from CSS reasoning alone - a `min-height: 0` fix that didn't address the actual bug, then a `window.innerHeight`-based JS layout-fit that was solving for the wrong direction of the problem (it can only raise a floor, and the real bug was content overflowing past one). After two wrong guesses, switched to driving a real headless Chrome instance already installed on the machine (`--headless=new --dump-dom` with a small diagnostic script measuring real `offsetHeight`/`clientHeight` values, and later `--screenshot` for an actual visual check) instead of continuing to reason from static CSS alone. That's what found both real bugs on the first try: `.chart-line`'s `flex: 1 1 auto` and the `clientHeight`-includes-padding mismatch. Worth remembering for next time a layout bug resists two rounds of CSS-only reasoning - measure first.

Closed by the operator after several more rounds beyond the initial card/resize work above - the empty-data cards, bar-chart label sizing, Complete View paging/links, Detail Page navigation (Back button) and red-for-failed coloring all landed in the same ticket rather than splitting off, since each grew directly out of reviewing the previous round's rendered result.

Measuring the bar-overflow bug needed a different headless-Chrome technique than the `--dump-dom` one used earlier in this ticket: a Google Chart draws asynchronously (CDN load + `setOnLoadCallback` + `redraw()`), and `--dump-dom`/`--virtual-time-budget` snapshots the DOM before that finishes rather than waiting for it. Switched to driving Chrome via `--remote-debugging-port` and the DevTools Protocol directly (a small Node script opening a WebSocket to the page's `webSocketDebuggerUrl` and sending `Runtime.evaluate`), polling until the chart's `<svg>` actually existed before reading `getBoundingClientRect()`/`clientHeight` on the container vs. the drawn SVG. That comparison - container's border-box bottom vs. the SVG's own bottom edge - is what pinned the exact 20px (one padding side) overflow and confirmed the fix. Also worth remembering: headless Chrome given a `file://` path under a directory whose name contains a space (this machine's Temp scratchpad, under `Jeff Talbot`) silently fails to load (`chrome-error://chromewebdata/`) even though the URL is percent-encoded - copying the probe file to a space-free path (e.g. under the repo root) fixed it.
