## Destination

A design/spec for the Dashboard reporting layer — delivery mode, page-generation architecture, query/data-layer design, and configuration shape — locked well enough to hand off as implementation work for a new Reports project in this solution. This map produces decisions, not the built Dashboard itself.

## Notes

- Full literal report inventory (every chart/table the Dashboard must show): [requirements.md](requirements.md).
- Domain vocabulary for this effort (Dashboard, Regeneration Run, Included Root, Detail Page, Leaderboard) is now in `CONTEXT.md` under "### Reporting" — use those terms, not synonyms.
- Settled architecture (from grilling on 2026-09-12; rationale for the reversible-feeling ones is in the linked ADRs):
  - Delivery: pregenerated static HTML, rebuilt in full on every Regeneration Run — no incremental updates. ([ADR-0005](../../docs/adr/0005-pregenerate-dashboard-as-static-html.md))
  - Trigger: a Regeneration Run is chained onto the existing daily CLI import — no independent schedule.
  - Charting library: Google Charts — `AnnotatedTimeLine` for single-series time charts, `LineChart` for Summary's multi-Root overlay, `BarChart` for Top-50 Leaderboards, `google.visualization.Table` for every full list. Matches the user's prior tool (`CGI.ArcGIS.Server.StatisticsAnalyzer.Console`, sample output at `C:\Temp\2026\ServiceAverageResponse\*.htm` / `ServiceUsage\*.htm`) — consult those files before redesigning any chart. CDN-loaded; viewers are assumed to have internet access.
  - Navigation: a persistent sidebar (not breadcrumbs/tabs) — Summary / Portal / ArcGIS Server (one group per Included Root) / Leaderboard, with "All" and "Last 7 Days" as separate pages per metric, not an in-page toggle. No "Home" sidebar entry — first load and the sidebar brand both resolve to Summary → Successful Requests → All. Full structure: [ticket 01](issues/01-page-generation-and-site-map.md).
  - Every page carries a "Created on `<generation timestamp>` / Generated by `<tool>`" footer, baked in as static text at Regeneration Run time.
  - Access: no authentication or per-viewer filtering — every viewer sees every Included Root. ([ADR-0006](../../docs/adr/0006-no-authentication-on-dashboard.md))
  - Included Roots: a new allow-list config owned by the Reports project itself, applied at report-generation time, not at ingest. ([ADR-0007](../../docs/adr/0007-root-allow-listing-lives-in-reports-project.md)) The user already has this list compiled.
  - Time range: "evolution through the year" charts are calendar-year-to-date, resetting each January, even though the aggregate database itself accumulates across multiple years.
  - Project home: new project in this same solution (working name "Reports"), alongside the existing Cli/Domain/Data projects.
  - Scale (real production numbers, from the user — corrects the original estimate, which was drawn from the checked-in `2026/` corpus and the `C:\Temp\2026\...` sample pages, both small/non-representative): 922,000,000 hits in 2025; 14 Included Roots (fixed/administrative, confirmed accurate — see [ticket 04](issues/04-included-root-config-shape.md)); ~20,000 distinct Portal Items; ~4,000 distinct ArcGIS Server services (~2,000 in the `arcgis` Root alone, ~2,000 spread unevenly across the other 13 Roots — e.g. `rhea` ≈ 5, `titan` ≈ 400). One static file per service/item is still the plan (~24,000 Detail Pages) — see [ticket 06](issues/06-chart-table-edge-cases.md) for how this reshaped the Complete View sizing.
- Consult `docs/agents/domain.md` conventions and `CONTEXT.md` before any ticket that touches naming.
- Tickets in this map are decisions/specs, not the build — see Destination.

## Decisions so far

- [Sortable table approach](issues/02-sortable-table-approach.md) — `google.visualization.Table` (native sort, matches the user's prior tool); supersedes this ticket's original hand-rolled-script recommendation.
- [Page generation & site map](issues/01-page-generation-and-site-map.md) — sidebar-only nav (Summary/Portal/ArcGIS Server/Leaderboard), All/Last-7-Days as separate pages, ArcGIS Server Complete View is the sole path to a service Detail Page, generation-timestamp footer on every page, chart types matched to the user's prior Google Charts tool. **Amended twice**: Portal's item table is an uncapped Complete View (was Top 500); both it (~20,000 rows) and the ArcGIS Server section-wide Complete View (~4,000 rows) ship uncapped with `google.visualization.Table`'s built-in paging, a settled decision once the real row counts were known (not a provisional "try and see").
- [Query and rollup data layer](issues/03-query-and-rollup-data-layer.md) — extend `Data`'s `AggregateQueryBase` (no new project, no rollup table); SQL views only for genuine cross-entity rollups; every line-chart point is a per-day value (never cumulative), totals/leaderboards use `SUM(time)/SUM(hits)` over year-to-date, one query per Leaderboard variant; year-to-date boundary computed once per run in .NET via a new injectable clock; Root-level charts drop the success/fail split (volume only).
- [Included Root config shape](issues/04-included-root-config-shape.md) — flat lowercase 14-name allow-list in Reports' `appsettings.json`, gating the ArcGIS Server section only; Portal shown unconditionally via the existing `PortalWebAdaptorName` setting (no Root column on that table to filter); `proxy` excluded to avoid double-counting; unlisted Roots silently excluded, no display-name field, no "other" rollup.
- [Portal item display naming](issues/05-portal-item-display-naming.md) — no title resolution (titles change too often to make caching worthwhile); raw `portal_item_id` shown everywhere, linked to the item's live Portal page via a new `PortalBaseUrl` setting.
- [Chart/table edge cases](issues/06-chart-table-edge-cases.md) — surfaced the real production scale (see Notes); no explicit tie-breaking anywhere (Tables are viewer-sortable, BarCharts already sort by the primary measure); under-full Leaderboards just render fewer rows/bars (the common case for small Roots, not a corner case); sparse-data entities' line charts span only their real date range, no zero-padding at either end.
- [Hosting and deployment](issues/07-hosting-and-deployment.md) — no decision needed; relative-linked static HTML works identically from a shared folder or an IIS site, and the user already has deployment infrastructure in place. Out of scope for this map beyond producing the file tree.
